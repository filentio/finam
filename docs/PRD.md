# PRD — сервис HH: поиск вакансий → черновик → отклик с сопроводительным (MVP)

## 1. Overview (что строим, для кого)
Мы строим сервис для соискателей, который:
- по заданным параметрам **профиля поиска** на hh.ru находит **вакансии** через официальные API;
- ранжирует найденные вакансии по релевантности;
- для выбранной вакансии создаёт **черновик письма** (сопроводительное письмо);
- позволяет отправить **отклик** на hh.ru **только после явного одобрения пользователем** (human-in-the-loop).

Авторизация и отправка откликов выполняются **только через HH OAuth**. Пароль/логин пользователя HH **не запрашиваем и не храним**.

Ключевые термины (используются во всех документах):
- **вакансия** — объект hh.ru, на который можно отправить отклик;
- **профиль поиска** — набор параметров поиска вакансий (ключевые слова, локации, фильтры и т. п.);
- **черновик письма** — сгенерированное сопроводительное письмо, доступное для просмотра/редактирования;
- **одобрение** — действие пользователя “разрешить отправку отклика”;
- **отклик** — отправка резюме + сопроводительного письма на вакансию через hh.ru.

Целевая аудитория:
- активные соискатели, которые ищут вакансии по понятным параметрам и хотят быстрее готовить качественные отклики, сохраняя контроль отправки.

## 2. Goals (цели) + KPI (метрики успеха)
Цели MVP:
- Сократить время на подготовку отклика за счёт поиска/ранжирования вакансий и генерации черновика письма.
- Обеспечить безопасную и корректную интеграцию с hh.ru через OAuth без хранения паролей.
- Обеспечить полный контроль пользователя над отправкой (обязательное одобрение).

KPI (целевые метрики на 1-й релиз / пилот):
- **Time-to-First-Response**: медианное время от запуска поиска до первого отправленного отклика ≤ 10 минут.
- **Draft usefulness**: ≥ 60% черновиков письма отправляются с правками ≤ 30% текста (признак качества основы).
- **Approval compliance**: 100% откликов отправлены только после одобрения (отсутствие автосенда).
- **Duplicate rate**: 0% повторных откликов на одну и ту же вакансию тем же резюме из сервиса.
- **OAuth success rate**: ≥ 95% успешных авторизаций без ручных вмешательств.
- **Error rate**: доля неуспешных отправок (не 2xx от HH) ≤ 2% при корректных входных данных.

## 3. In/Out of Scope (что входит в MVP, что НЕ входит)
In scope (MVP):
- HH OAuth (авторизация пользователя).
- Создание/редактирование профиля поиска.
- Поиск вакансий на hh.ru по профилю поиска.
- Ранжирование вакансий (rule-based/эвристики).
- Просмотр карточки вакансии и причин ранжирования (простая объяснимость).
- Генерация черновика письма под вакансию и выбранное резюме пользователя (по `resume_id` в HH).
- Редактирование черновика письма пользователем.
- Отправка отклика через HH API только после одобрения.
- История откликов и статусы (минимум: draft / approved / queued / sent / failed).
- Антидубли (не отправлять второй раз на ту же вакансию тем же резюме).
- Лимиты и quiet hours (ограничение отправок и “тихие часы”).

Out of scope (для MVP не делаем):
- Автоматический массовый автосенд без подтверждения.
- Интеграции с другими площадками (LinkedIn, Indeed, Telegram-каналы и т. п.).
- Сложный ML/embeddings, персональные модели, обучение на данных пользователя (может быть позже).
- Хранение логина/пароля HH или обход OAuth.
- Обход антибот/скрейпинг через парсинг HTML вместо API.
- Командные аккаунты, мультипользовательские организации, роли кроме user/admin.
- Автогенерация/подбор резюме (создание резюме в HH) — только использование существующих резюме пользователя в HH.

## 4. User Stories (минимум 8–12 сценариев)
1. Как **пользователь**, я хочу авторизоваться через HH OAuth, чтобы сервис мог получать вакансии и отправлять отклики от моего имени без передачи пароля.
2. Как **пользователь**, я хочу создать профиль поиска (должность/ключевые слова/локации/зарплата/график), чтобы быстро повторять поиск.
3. Как **пользователь**, я хочу запустить поиск по профилю поиска и получить список вакансий, чтобы выбрать подходящие.
4. Как **пользователь**, я хочу видеть ранжированный список и краткое объяснение ранга, чтобы понимать, почему вакансия выше/ниже.
5. Как **пользователь**, я хочу открыть вакансию и выбрать резюме, чтобы подготовить отклик именно этим резюме.
6. Как **пользователь**, я хочу получить черновик письма под вакансию, чтобы быстрее отправить качественный отклик.
7. Как **пользователь**, я хочу отредактировать черновик письма перед отправкой, чтобы учесть нюансы и мой стиль.
8. Как **пользователь**, я хочу явно одобрить отправку, чтобы сервис не отправлял отклик без моего решения.
9. Как **пользователь**, я хочу видеть статус отклика (отправлен/ошибка), чтобы понимать результат действий.
10. Как **пользователь**, я хочу, чтобы сервис не отправлял отклик дважды на одну вакансию тем же резюме, чтобы избежать дублей и риска блокировок.
11. Как **пользователь**, я хочу настраивать стоп-листы (компании/ключевые слова), чтобы исключить нежелательные вакансии.
12. Как **админ**, я хочу видеть агрегированные метрики и журнал ошибок без персональных данных, чтобы контролировать стабильность и качество сервиса.

## 5. User Flow (текстовая схема шагов)
1) Пользователь открывает сервис → выбирает “Войти через HH”  
2) HH OAuth → пользователь подтверждает доступ → сервис получает токены  
3) Пользователь создаёт/выбирает профиль поиска  
4) Нажимает “Найти вакансии” → сервис вызывает HH API → получает вакансии  
5) Сервис применяет бизнес-правила (фильтры/стоп-листы/антидубли) → ранжирует  
6) Пользователь просматривает список → открывает вакансию  
7) Пользователь выбирает резюме → сервис генерирует черновик письма  
8) Пользователь просматривает/редактирует черновик письма  
9) Пользователь нажимает “Одобрить и отправить отклик”  
10) Сервис проверяет антидубли/лимиты/quiet hours → отправляет отклик через HH API  
11) Сервис сохраняет результат и показывает статус в истории откликов

## 6. Business Rules (фильтры, стоп-листы, антидубли, лимиты, quiet hours)
Фильтры (MVP):
- По параметрам профиля поиска: текст, регион/город, опыт, занятость, график, зарплата (если задана), удалёнка/офис (если доступно в HH).
- Фильтрация “только с откликом доступным через HH” (если HH различает типы взаимодействий).

Стоп-листы (MVP):
- **Стоп-лист компаний**: исключать вакансии по `employer_id` (и/или имени работодателя, если id не доступен).
- **Стоп-лист ключевых слов**: исключать вакансии, если в названии/описании встречаются слова/фразы (регистронезависимо).

Антидубли (MVP):
- Запрещено отправлять отклик, если уже есть запись об отклике со связкой: `(hh_user_id, vacancy_id, resume_id)` со статусом `sent` или `queued` (идемпотентность).
- Если пользователь повторно пытается отправить отклик на ту же вакансию тем же резюме — показывать понятное сообщение и предлагать открыть историю.

Лимиты (MVP, конфигурируемые):
- Лимит отправок: например, до **N откликов в день** на пользователя (значение задаётся конфигурацией, по умолчанию консервативное).
- Лимит генераций черновика письма: до **M черновиков в день** на пользователя.
- Лимиты запросов к HH API: троттлинг согласно рекомендациям/ограничениям HH; при превышении — очереди и ретраи с backoff.

Quiet hours (MVP):
- В “тихие часы” отправка отклика запрещена даже при одобрении: сервис сохраняет одобренный отклик в статусе `approved` и предлагает отправить позже.
- Quiet hours задаются в профиле пользователя или глобальной настройкой (по умолчанию выключены или безопасное окно, определяется политикой продукта).

## 7. Roles & Permissions (минимум: user/admin)
Роли:
- **user**: управляет профилями поиска, просматривает вакансии, создаёт/редактирует черновик письма, выполняет одобрение и отправку отклика, смотрит историю.
- **admin**: доступ к системным настройкам лимитов/quiet hours, мониторингу, агрегированным метрикам, журналу ошибок и аудиту отправок (без просмотра содержимого писем/PII, кроме случаев поддержки и при наличии процедур).

Права (MVP):
- Пользователь видит только свои профили поиска, черновики письма и историю откликов.
- Админ не может отправлять отклики от имени пользователя.

## 8. Data (какие данные о пользователе/вакансии храним; что нельзя хранить)
Храним (минимально необходимое для MVP):
- Идентификатор пользователя в нашей системе + связанный `hh_user_id` (если доступен через API).
- OAuth-токены HH (access/refresh) в зашифрованном виде, с метаданными срока действия.
- Профили поиска (параметры фильтров, стоп-листы).
- Список вакансий как “снимок” для истории/антидублей: `vacancy_id`, заголовок, работодатель (`employer_id`/название), ссылка, ключевые параметры (город, зарплата, опыт), время обнаружения.
- Черновик письма: текст, версия/ревизии, метаданные генерации (модель/шаблон, время).
- История откликов: `vacancy_id`, `resume_id`, статус, timestamps (draft/approved/sent/failed), причина ошибки (без PII), идентификатор операции (idempotency key).
- Аудит “кто и когда одобрил/отправил” (user_id, action, timestamp, vacancy_id, resume_id).

Не храним / запрещено:
- **Логин/пароль HH** в любом виде.
- Полный HTML/текст описания вакансии, если это запрещено ToS или не требуется для MVP (ориентируемся на условия HH API; в MVP сохраняем только необходимый минимум).
- Персональные данные сверх необходимого (например, телефон/почту из резюме) — если они возвращаются из API, не логировать и не сохранять без строгой необходимости.
- Сырые OAuth-данные в логах.

## 9. Risks & Mitigations (ToS/баны/качество писем/безопасность токенов)
Риски:
- Нарушение правил hh.ru (ToS), риск блокировок из-за агрессивной автоматизации.
- Превышение лимитов HH API или временные ошибки → деградация UX.
- Низкое качество черновиков письма (шаблонность, галлюцинации, неправильные факты).
- Компрометация OAuth-токенов → несанкционированные отклики.
- Отправка дублей (повторные отклики) → репутационные риски и риск ограничений со стороны HH.

Митигирующие меры (MVP):
- Использовать **официальные HH API** и соблюдать их ограничения; троттлинг, очереди, backoff.
- **Human approval обязателен**: никакой отправки без одобрения.
- Антидубли и идемпотентность отправки: запрет повторов для `(vacancy_id, resume_id)`.
- Черновик письма: генерация с явным запретом выдумывать факты; подстановка только проверяемых данных (название вакансии, работодатель, навыки из резюме — если разрешено) и обязательный экран предпросмотра/редактирования.
- Безопасность токенов: шифрование at-rest, минимальные права OAuth, ротация секретов, отсутствие токенов/PII в логах, аудит операций отправки.

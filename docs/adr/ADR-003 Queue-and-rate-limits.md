# ADR-003 Queue-and-rate-limits

## Title
Очереди, лимиты, ретраи и идемпотентность отправки отклика

## Status
Accepted

## Context
MVP выполняет внешние сетевые операции к HH API:
- поиск вакансий;
- получение деталей/данных аккаунта;
- отправка отклика.

Риски и требования:
- лимиты и rate limiting HH API (429), временные ошибки (5xx), нестабильность сети;
- запрет на дубли откликов на одну вакансию тем же резюме;
- “send” должен быть безопасен при повторных запросах (повторный клик/таймаут).

Синхронное выполнение “в лоб” в HTTP запросе UI ухудшает надёжность и усложняет соблюдение лимитов.

## Decision
- Все операции, которые могут быть долгими/неустойчивыми, выполняются через **фоновые задачи**:
  - поиск вакансий (`search.run`);
  - отправка отклика (`application.send`);
  - (опционально) генерация черновика письма (`cover.generate`).
- Реализуем **rate limiting** на уровне HH Connector (троттлинг) и на уровне воркера (ограничение параллелизма).
- Ретраим только транзиентные ошибки (429/5xx/timeouts) с exponential backoff и джиттером.
- Для отправки отклика вводим:
  - **уникальность** `applications` по `(user_id, vacancy_id, resume_id)` (антидубли);
  - **идемпотентность** `send` по заголовку `Idempotency-Key` (на пользователя и application_id) с сохранением результата.
- При успешной постановке в очередь статус отклика становится “в процессе отправки” (`queued`), а финальный результат фиксируется воркером.

## Consequences
Плюсы:
- устойчивость к 429/5xx и временным проблемам сети;
- предсказуемая нагрузка на HH API, меньше риск блокировок;
- отсутствие дублей при повторных попытках отправки.

Минусы/ограничения:
- требуется инфраструктура фоновых задач (воркер + хранилище очереди/таблица outbox);
- усложняется модель статусов и трассировка (нужны audit/метрики).

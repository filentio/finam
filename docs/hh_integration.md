# Интеграция с hh.ru (MVP)

## 1. Принципы MVP
- Используем **официальные HH API**.
- Авторизация и действия “от имени пользователя” выполняются только через **HH OAuth**.
- Логин/пароль HH не используем и не храним.
- В MVP режим **approve_and_send**: отклик отправляется только после **одобрения**.

## 2. Операции HH API, используемые в MVP
Ниже перечислены операции на уровне смысловых действий (без привязки к конкретным URL; конкретика зависит от документации HH API и может отличаться по названиям).

### 2.1 Поиск вакансий
Назначение: получить список вакансий под **профиль поиска**.

Входные параметры (из `filters_json` профиля поиска):
- текст запроса, регион/город, опыт, занятость, график, зарплата и т. п.

OAuth:
- как правило, поиск вакансий может выполняться **без OAuth** (публичные данные);
- в MVP допускается выполнять поиск без OAuth, но при наличии подключённого HH OAuth можно использовать токен, если HH API даёт расширенные возможности/лимиты (уточняется).

### 2.2 Детали вакансии
Назначение: открыть карточку **вакансии** в UI, определить применимость отклика через API.

OAuth:
- обычно можно **без OAuth** (публичная карточка вакансии);
- если HH API ограничивает часть полей без OAuth, backend использует OAuth при наличии.

Выход:
- нормализованные поля + флаг:
  - `apply_via_hh=true` если отклик через HH API поддерживается;
  - `apply_via_hh=false` если отклик внешний/ограничен (UI показывает `external_apply_url`).

### 2.3 Резюме пользователя (для выбора resume_id)
Назначение: дать пользователю выбрать `resume_id`, который будет приложен к **отклику**.

OAuth:
- требуется **OAuth**, т.к. это данные пользователя.

Политика данных:
- в нашей БД сохраняем только `resume_id` (идентификатор), без содержания резюме и контактных данных.

### 2.4 Отправка отклика
Назначение: отправить **отклик** на вакансию с выбранным `resume_id` и текстом (черновиком письма).

OAuth:
- требуется **OAuth** (действие от имени пользователя).

Ограничения:
- отправка доступна только при статусе `approved` (human-in-the-loop).
- антидубли на уровне сервиса: запрет повторной отправки на ту же вакансию тем же резюме.

## 3. OAuth: токены, refresh, re-auth

### 3.1 Flow
MVP использует классический OAuth flow:
- backend инициирует OAuth (`/auth/hh/start`) с параметрами `state` (и PKCE, если требуется HH для public clients);
- HH возвращает `code` → backend обменивает `code` на токены;
- backend сохраняет токены в `hh_accounts` в зашифрованном виде.

### 3.2 Access/refresh
Если HH выдаёт refresh token:
- access token используется для запросов к HH API;
- при истечении access token backend выполняет refresh и обновляет `token_expires_at`.

Если refresh token отсутствует (или refresh недоступен):
- при 401/invalid token backend переводит интеграцию в `reauth_required` и просит пользователя переподключить HH OAuth.

### 3.3 Re-auth (повторная авторизация)
Сервис переводит HH интеграцию в `reauth_required`, если:
- refresh не удался (например, токен отозван);
- HH возвращает устойчивый 401 для OAuth-запросов.

UI поведение:
- показывать баннер/статус “нужно переподключить HH”;
- блокировать действия, требующие OAuth (отправка отклика, список резюме).

## 4. Смена HH аккаунта (“под другим пользователем”)
Цель: пользователь может переподключить HH OAuth на другой HH аккаунт.

UX-флоу (уровень сервиса):
1) Пользователь открывает настройки интеграций → “Отключить HH”  
2) Backend выполняет `POST /auth/hh/disconnect`:
   - удаляет токены (ciphertext) или делает их недоступными;
   - помечает `hh_accounts.status=disconnected`;
3) UI предлагает “Подключить другой HH аккаунт” → `GET /auth/hh/start`  
4) После callback backend создаёт/обновляет `hh_accounts` и фиксирует событие в `audit_log`.

Важно:
- История откликов в нашем сервисе сохраняется у пользователя сервиса.
- При смене HH аккаунта возможно, что `resume_id` старого HH аккаунта станет недействительным; при отправке отклика backend должен валидировать доступность `resume_id` и возвращать `VALIDATION_ERROR` или специализированный код (например, `RESUME_NOT_FOUND`, если введём).

## 5. Обработка ошибок HH и лимитов

### 5.1 401 (Unauthorized)
Сценарии:
- access token истёк → пробуем refresh (если доступно) и повторяем запрос;
- токен отозван/невалиден → переводим `hh_accounts.status=reauth_required`.

Ретраи:
- допустим 1 повтор запроса после refresh (без бесконечных циклов).

### 5.2 403 (Forbidden)
Сценарии:
- недостаточно прав по scope;
- ограничения аккаунта/действия запрещены;
- иные запреты HH.

Поведение:
- не ретраить автоматически;
- для отправки отклика: `applications.status=failed`, `error_code=HH_FORBIDDEN`;
- в UI — понятное сообщение и рекомендация проверить доступ/настройки на hh.ru.

### 5.3 429 (Rate limit)
Поведение:
- фоновые задачи применяют backoff + джиттер;
- троттлинг на уровне HH Connector;
- метрика и алерт при росте 429.

Для отправки отклика:
- статус остаётся `queued` до исчерпания ретраев;
- при исчерпании — `failed` с `HH_RATE_LIMITED` или `HH_UNAVAILABLE` (в зависимости от политики).

### 5.4 5xx / timeouts
Поведение:
- ретраи в воркере с backoff и лимитом попыток;
- при исчерпании — `failed` с `HH_UNAVAILABLE`.

### 5.5 “Капча/антибот/подозрительная активность”
Если HH сообщает о необходимости ручного действия (капча/верификация) либо запросы начинают стабильно блокироваться:
- прекращаем автоматические ретраи отправки;
- переводим HH интеграцию в `reauth_required` или специальный статус (если будет введён) и показываем в UI инструкцию “требуется действие на hh.ru”.

Примечание:
- в MVP не пытаемся обходить антибот механизмы.

## 6. Применимость вакансии (external apply)
Если вакансия не поддерживает отправку отклика через HH API:
- Normalizer выставляет `apply_via_hh=false` и сохраняет `external_apply_url` (если есть);
- UI показывает ссылку на внешний отклик;
- endpoint `applications.send` возвращает `409 VACANCY_NOT_APPLICABLE`.

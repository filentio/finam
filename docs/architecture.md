# Архитектура MVP (approve_and_send) — hh.ru

## 1. Принципы и ограничения MVP
- Термины: **вакансия**, **профиль поиска**, **черновик письма**, **одобрение**, **отклик** (как в документах этапа 1).
- Единственный режим MVP: **approve_and_send** — отправка отклика возможна только после **одобрения** пользователем.
- Авторизация и отправка откликов: **только HH OAuth**, логин/пароль HH не используем и не храним.
- Интеграция только с **hh.ru** (в MVP).
- Архитектура расширяемая: новые источники, режимы и правила добавляются через интерфейсы/контракты без переписывания ядра.

## 2. Компоненты (MVP) и границы ответственности

### UI (веб/клиент)
Ответственность:
- HH OAuth вход (переход на старт OAuth, обработка результата на стороне UI).
- CRUD профилей поиска.
- Просмотр ранжированного списка вакансий и карточки вакансии.
- Генерация/редактирование черновика письма.
- Экран “одобрение” и запуск отправки отклика.
- История откликов и статусы.

Не делает:
- прямых вызовов HH API (только через backend).

### Backend API (BFF / Application API)
Ответственность:
- единые REST API контракты для UI;
- проверка прав доступа, лимитов, quiet hours;
- создание сущностей: профили поиска, черновики письма, отклики, аудит;
- постановка фоновых задач (поиск/обновление/отправка) в очередь;
- идемпотентность критичных операций (в первую очередь `send`).

### Secrets/Auth
Ответственность:
- хранение секретов HH OAuth (client_id/client_secret при необходимости) и ключей шифрования;
- шифрование/дешифрование OAuth токенов (envelope encryption или application-level encryption);
- управление сессиями пользователей (наша авторизация) и связкой с HH аккаунтом.

### Storage (Postgres)
Ответственность:
- хранение данных MVP: пользователи, HH аккаунты (токены), профили поиска, вакансии (нормализованные поля + ограниченный raw_json), матчи/скоринг, черновики писем, отклики, аудит, идемпотентность.

### HH Connector
Ответственность:
- абстракция доступа к HH API (HTTP клиент, ретраи, троттлинг, refresh токена);
- операции: поиск вакансий, детали вакансии, получение резюме пользователя (если нужно для выбора), отправка отклика;
- преобразование HH ошибок в нормализованные error_code для ядра.

Граница:
- HH Connector не содержит бизнес-правил ранжирования/лимитов; он “тупой” адаптер к внешнему API.

### Normalizer
Ответственность:
- нормализация данных HH в внутренний формат **вакансии**:
  - выделение полей для отображения, фильтрации, антидублей;
  - вычисление derived-полей (например, “можно ли отправить отклик через HH API”).
- политика raw_json: сохранять только минимум, необходимый для трассировки и повторного воспроизведения (с ограничением по времени хранения).

### Matcher / Ranker
Ответственность:
- применение правил профиля поиска (фильтры/стоп-листы);
- скоринг и ранжирование вакансий;
- формирование “причин” (`reasons_json`) для объяснимости ранга.

### Cover Letter Service
Ответственность:
- генерация **черновика письма** по (вакансия + выбранное резюме + профиль поиска/шаблон);
- хранение шаблонов (MVP: минимально) и ревизий черновика письма;
- гарантии качества: запрет выдумывать факты, использование только разрешённых данных.

### Apply Orchestrator
Ответственность:
- реализация конечного автомата отклика (draft → approved → отправка → sent/failed);
- проверки перед отправкой: антидубли, лимиты, quiet hours, применимость вакансии (can_apply);
- идемпотентность операции “send” (в связке с API и БД);
- постановка задачи отправки в очередь и обработка результата HH API.

### Queue / Background Workers
Ответственность:
- выполнение фоновых задач:
  - `search.run` — поиск вакансий по профилю поиска;
  - `match.compute` — скоринг/ранжирование (может быть частью `search.run`);
  - `cover.generate` — генерация черновика письма (опционально async);
  - `application.send` — отправка отклика после одобрения.

Примечание про статусы:
- В MVP состояние **“в очереди/в процессе отправки”** фиксируется статусом `queued`, при этом UI показывает “отправляется”.

### Observability
Ответственность:
- структурированные логи без PII и без содержимого черновика письма;
- метрики: успех/ошибки HH вызовов, latency, количество отправок, rate-limit события;
- алерты: рост 429/5xx, рост failed отправок, аномалии по дублям.

## 3. Потоки данных (MVP)

### 3.1 Поиск вакансий → нормализация → матчинг/скоринг
1) UI вызывает `POST /search-profiles/{id}/run`  
2) Backend создаёт `search_run` (если используется) и ставит задачу `search.run` в очередь  
3) Worker вызывает HH Connector (поиск вакансий)  
4) Normalizer преобразует HH payload в внутренние поля, создаёт/обновляет записи `vacancies` (уникальность: `(source, external_vacancy_id)`)  
5) Matcher/Ranker применяет фильтры/стоп-листы и рассчитывает `matches` (score + reasons_json)  
6) UI получает список вакансий с score/reasons через `GET /vacancies?...`

### 3.2 Генерация черновика письма
1) UI выбирает вакансию и резюме → `POST /cover-letters/generate`  
2) Backend валидирует доступ/применимость вакансии  
3) Cover Letter Service генерирует черновик письма (sync или job `cover.generate`)  
4) Результат сохраняется в `cover_letters` (draft) и возвращается UI  
5) UI позволяет редактировать → `PATCH /cover-letters/{id}`

### 3.3 Одобрение → отклик через HH OAuth
1) UI создаёт (или использует существующий) объект `applications` со статусом `draft`  
2) Пользователь выполняет **одобрение** → `POST /applications/{id}/approve` (статус `approved`, запись в `audit_log`)  
3) Пользователь запускает отправку → `POST /applications/{id}/send` с `Idempotency-Key`  
4) Apply Orchestrator:
   - проверяет антидубли (уникальность `(user_id, vacancy_id, resume_id)`), лимиты, quiet hours, can_apply;
   - переводит статус в `queued` и ставит задачу `application.send` в очередь
5) Worker отправляет отклик через HH Connector (OAuth токен)  
6) По результату: `sent` или `failed`, фиксируется `external_application_id` (если HH возвращает), запись в `audit_log`

## 4. Очереди/фоновые задачи (назначение)
Почему очередь нужна в MVP:
- соблюдение лимитов HH API и троттлинг;
- ретраи транзиентных ошибок (429/5xx/timeouts);
- разрыв UI-взаимодействия и длительных сетевых операций.

Минимальные типы задач:
- `search.run(search_profile_id, user_id)`
- `application.send(application_id, user_id, idempotency_key)`
- (опционально) `cover.generate(vacancy_id, resume_id, user_id)`

Требования к задачам:
- идемпотентность на уровне обработчиков (повторное выполнение не создаёт дублей);
- лимит параллелизма и rate-limits на HH Connector;
- дедупликация задач отправки по application_id.

## 5. Стратегии расширения (после MVP)

### 5.1 Добавление новых источников вакансий
Вводим интерфейс `SourceConnector` (абстракция):
- `searchVacancies(profile)` → список внешних вакансий
- `getVacancyDetail(external_id)`
- `canApply(vacancy)` + `apply(application)` (если источник поддерживает отклик)

Каждый источник реализует:
- connector (HTTP/SDK)
- normalizer (маппинг полей)
- правила применимости/ограничения ToS

### 5.2 Добавление режимов работы
Режимы как feature-flag/политика в Apply Orchestrator:
- `approve_and_send` (MVP)
- `draft_only` (запрет send на уровне API/оркестратора)
- `auto_send` (будущий режим; требует отдельной политики безопасности и ToS)

### 5.3 Добавление правил ранжирования
Matcher/Ranker строится как цепочка правил:
- базовые фильтры (стоп-листы, параметры профиля поиска)
- скоринговые факторы (веса конфигурируемы)
- объяснимость: каждая прибавка/штраф оставляет “след” в `reasons_json`

## 6. Открытые вопросы (минимально)

- Какие HH scopes и какие точные лимиты API (RPS/сутки) критичны для sizing и политики ретраев?
